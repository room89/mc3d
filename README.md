Monte-Carlo 3D Flow Solver
===========================

MC3D — экспериментальный решатель разреженных потоков, основанный на
стохастическом моделировании движения и столкновений частиц в трёхмерной
области. Код исторически писался для исследовательских задач и сейчас находится
в процессе модернизации (перевод на современный стиль C++, чистка API и
инфраструктуры сборки).

## Возможности
- геометрия твёрдого тела, задаваемая наборами полигонов (генерация клина,
  пирамиды, куба либо импорт STL);
- сетка ячеек (`CellCluster`) с контролем граничных условий
  (зеркальные, периодические, свободные, «гипер-свободные»);
- моделирование движения частиц, столкновения, сбор статистики по ячейкам;
- запись данных по плотности, скоростям, времени шага.

## Сборка
```bash
make build
```

Исполняемый файл `MC3dSolver` находится в директории `build/`.

Доступные команды Makefile:
```bash
make help
make test
make run-example
make run CONFIG=configs/example.json ARGS="--end-time 0.1"
make run-smoke
make run-example OUTPUT_DIR=results/example
make clean
```

`make run` запускает расчёт с выбранным конфигурационным файлом; дополнительные
параметры командной строки можно передать через `ARGS`. `make run-example`
использует демонстрационный набор `configs/example.json`, а `make run-smoke`
запускает короткий расчёт на маленькой сетке без геометрии тела. Все файлы,
созданные при запуске через Makefile, сохраняются в `output/`; каталог можно
переопределить, например `OUTPUT_DIR=results/example`.

Проверки запускаются командой `ctest --test-dir build --output-on-failure`.
Каждый тест GoogleTest зарегистрирован в CTest отдельно, поэтому имя
упавшего теста видно в отчёте CI. На Ubuntu 24.04 CI собирает Release
с GCC 14 и Debug с Clang 18, AddressSanitizer и UndefinedBehaviorSanitizer.
Отдельная Debug-сборка с GCC 14 и ThreadSanitizer проверяет гонки потоков.
Тесты столкновений и параллельного расчёта дополнительно повторяются трижды
в Release-сборке.
Тесты проверяют ограничение шага времени по каждой оси, периодический перенос
на всех шести гранях (включая точные попадания и несколько длин области),
а также сохранение числа частиц, суммарного импульса и кинетической энергии.
Сохранение проверяется для столкновений и после каждого шага в замкнутой
периодической области без тела при одном и четырёх рабочих потоках.
Импульс и энергия считаются для одинаковых частиц единичной массы;
число частиц должно совпадать точно, для сумм используется численный допуск.

В сценарии `make run` грани по Z открыты (`hyperfree`), поэтому общее число
частиц может меняться: выходящие частицы удаляются, а приток задаётся
параметрами внешнего газа. Дробный приток накапливается отдельно для каждой
граничной ячейки между шагами, включая шаги с притоком меньше одной частицы.
Граница `free` выдаёт накопленный приток порциями не менее трёх частиц для
нормировки температуры генератором; `hyperfree` может добавлять по одной.

Для визуальной диагностики обтекания куба используйте `configs/body_flow.json`:
сетка 80×40×20, около миллиона частиц, вход по X, выход по X и периодические
боковые границы. Выполните из корня проекта после сборки:

```bash
mkdir -p build/flow-body build/flow-control
(cd build/flow-body && ../MC3dSolver --config ../../configs/body_flow.json > run.log 2>&1)
(cd build/flow-control && ../MC3dSolver --config ../../configs/body_flow.json --geometry-type none > run.log 2>&1)
python3 tools/body_flow_report.py --config configs/body_flow.json \
  --body build/flow-body --control build/flow-control --out build/flow-report
```

Скрипту нужны `numpy`, `pandas`, `matplotlib` и `pillow`. Он создаёт четыре PNG,
две GIF, временные ряды CSV и `summary.json`. Карты показывают среднее по
снимкам за последнюю треть прогона, GIF — скользящее среднее по трём снимкам.
Цветовые шкалы фиксированы; куб отмечен отдельно, пространственная
интерполяция не применяется. Отчёт рассчитан на этот сценарий с кубом и
центрированной областью; для повторного запуска используйте пустые каталоги.
Случайные реализации могут различаться между запусками.

Это качественная диагностика, а не подтверждение точности физической модели.
`hyperfree` использует равномерное распределение скоростей, контроль без тела
показывает дрейф средней скорости и числа частиц. На результат также влияют
периодические копии тела; позднее усреднение не означает установившееся течение.

Ячейки используют интервалы `[нижняя грань, верхняя грань)`: частица на
внутренней грани принадлежит следующей ячейке, а на верхней периодической
грани переносится на нижнюю. Последний шаг ограничивается оставшимся
временем до `end_time`.

## Запуск
```bash
./build/MC3dSolver [опции]
```

Все параметры расчёта теперь можно задать либо из командной строки, либо через
конфигурационный файл. Если параметры не указаны, используются значения по
умолчанию (аналогичные старому сценарию в `main.cpp` с гипер-свободными
границами).

### Примеры CLI
- задать размеры области и число ячеек:
  ```bash
  ./build/MC3dSolver --lx 2.0 --ly 1.0 --lz 0.5 --ncx 40 --ncy 20 --ncz 10
  ```
- выбрать тип граничных условий:
  ```bash
  ./build/MC3dSolver --boundary-x-neg mirror --boundary-x-pos mirror \
      --boundary-y-neg periodic --boundary-y-pos periodic \
      --boundary-z-neg free --boundary-z-pos free
  ```
- выбрать геометрию тела:
  ```bash
  ./build/MC3dSolver --geometry-type wedge --geometry-wedge-alpha 0.349
  ```

### Конфигурационный файл
Любую опцию можно перенести в JSON-файл:
```json
{
  "lx": 1.5,
  "ly": 1.0,
  "lz": 1.0,
  "ncx": 24,
  "ncy": 16,
  "ncz": 8,
  "np": 80,
  "kn": 0.03,
  "cu": 0.5,
  "end_time": 2.0,
  "boundary_x_neg": "mirror",
  "boundary_x_pos": "mirror",
  "geometry_type": "cube",
  "geometry_cube_width": 0.4,
  "geometry_cube_length": 0.4,
  "geometry_cube_height": 0.4
}
```

Запуск с файлом:
```bash
./build/MC3dSolver --config sample_config.json
```
Опции из командной строки имеют приоритет над значениями из файла и могут
дополнять несколько файлов `--config`. См. также готовый пример
`configs/example.json`.

Помимо JSON поддерживается упрощённый YAML (плоские ключи вида `ключ: значение`)
и старый формат `ключ = значение` — все варианты можно комбинировать.

В ходе выполнения в корне проекта появятся файлы `data*.dat`, `speed.dat`,
`time.dat`, `*.net`.

## Структура исходников
- `src/cell.*`, `src/cell_cluster.*` — ядро solver'а (ячейки, кластеры, шаги по
  времени);
- `src/boundary*`, `src/free_boundary*` — граничные условия;
- `src/geometry.*`, `src/poligon.*` — построение и обработка геометрии;
- `src/particle.*` — модель частицы и логика столкновений;
- `src/utils/` — вспомогательный код (логгер, таймер, потоковый пул, генератор
  случайных чисел);
- `src/warning.*`, `src/exception.*`, `src/exit_code.h` — обработка исключительных
  ситуаций;
- `tools/clang-format.sh` — массовое форматирование.

При столкновении с телом проверяется весь отрезок движения частицы и
обрабатывается первое пересечение с треугольником поверхности, даже если
треугольник находится за пределами исходной ячейки. Проверка принадлежности
точки телу поддерживает невыпуклые замкнутые сетки; для открытых или
самопересекающихся STL результат не определён. После каждого шага решатель
выводит предупреждение с числом частиц внутри тела, если такие обнаружены.
Допуски пересечения и смещения зависят от масштаба геометрии и точности
координат. Нормаль столкновения вычисляется по вершинам треугольника.
Если за один шаг требуется более 32 столкновений одной частицы или не удаётся
вывести частицу из тела, расчёт завершается с ошибкой. В случае лимита
столкновений следует уменьшить `cu`, чтобы сократить шаг по времени.

## Визуализация результатов

### Быстрый просмотр полей и анимации

После завершения расчёта постройте плотность `ro`, температуру `T` и
продольную скорость `vx`, а также GIF температуры одной командой:

```bash
# Зависимости (в активном Python-окружении):
python -m pip install numpy pandas matplotlib pillow
python tools/plot_fields.py output/wedge-preview --gif
open output/wedge-preview/plots
```

Укажите фактический каталог своего запуска. Скрипт читает `final.dat` для
PNG и `data*.dat` для GIF; поддерживаются текстовые и бинарные снимки.
Результаты: `plots/ro_xy.png`, `plots/T_xy.png`, `plots/vx_xy.png` и
`plots/temperature.gif`. Без `--gif` создаются только PNG.
По умолчанию выбирается один слой ячеек XY, ближайший к `z=0`
(при равном расстоянии — положительный). `--plane xz --slice 0.1`
выбирает слой рядом с `y=0.1`, `--out PATH` меняет каталог результата.
Шкала температуры GIF фиксирована от 0 до 12; её можно изменить через
`--vmin` и `--vmax`. PNG имеют собственные автоматические шкалы.
Это мгновенные поля без временного усреднения и без контура тела;
интерполяция между центрами ячеек может сглаживать особенности у стенки.

### Нагрев полигонов и силы на теле

Параметр `wall_heat_capacity` (CLI: `--wall-heat-capacity`) включает
динамическую температуру каждого треугольника. `wall_temperature` задаёт
начальную температуру. Без теплоёмкости стенка остаётся изотермической.
Значения обоих параметров должны быть конечными и положительными;
для нагрева нужна непустая геометрия без вырожденных треугольников.

`wall_heat_capacity` — **общая** теплоёмкость поверхности в нормированных
единицах решателя, где плотность невозмущённого газа равна 1, а энергия
частицы на единицу массы равна `v²/2`. Это не значение в Дж/К без перевода
единиц. Теплоёмкость треугольника `Ci = Ctotal * Ai / Atotal` соответствует
одинаковому материалу и толщине прогреваемого слоя по всей поверхности.
Это независимые тепловые элементы: теплопроводность между ними, излучение
и теплоотвод внутрь тела пока не моделируются. Мелкие треугольники имеют
меньшую теплоёмкость и более шумную температуру; измельчение STL требует
проверки статистики и шага времени.

При отражении накапливается `ΔQi = w * (vin² - vout²) / 2`, где
`w = 1 / ReferenceParticleDensity(config)`. Поэтому увеличение `np` или
числа ячеек не меняет физический вес газа. В течение шага все отражения
используют температуру начала шага; после завершения рабочих потоков
обновляется `Ti += ΣΔQi / Ci`. Газ может нагревать и охлаждать поверхность.
Если новая температура неположительна или не конечна, расчёт завершается
с ошибкой, без обрезки температуры и потери баланса энергии. Уменьшите `Cu`
и проверьте сходимость; теплоёмкость следует выбирать по модели материала.
Даже положительная температура не гарантирует точность большого теплового шага.

Рядом с каждым обычным снимком появляется файл `<snapshot>.surface.csv`
(включая `initial.dat.surface.csv` и `final.dat.surface.csv`): время,
индекс и вершины треугольника, температура, теплоёмкость и суммарное тепло
`absorbed_heat` со знаком плюс при нагреве. Формат газовых снимков не меняется.

Для любой непустой геометрии `body_loads.csv` записывает каждый шаг:
`Fx/Fy/Fz = w * Σ(vin - vout) / dt` и средние с начала расчёта
`mean_F* = Σ(F*dt) / t`. Это сила **газа на тело** в нормированных единицах,
включающая нормальную и касательную передачу импульса; режим нагрева
для её вычисления не обязателен. Средние включают начальный переходный
процесс. Для установившихся характеристик усредняйте позднее окно по `dt`.

При заданном `force_reference_area` (`--force-reference-area`) добавляются
`Cx/Cy/Cz = Fx/Fy/Fz / (q∞ * Aref)` и их средние, где
`q∞ = U∞²/2 = S²*T∞`. Площадь должна быть положительной и конечной,
скорость потока — ненулевой. В CSV сохраняются площадь, скоростной напор
и угол потока. Оси `Cx/Cy` — глобальные X/Y; дополнительно `Cd` направлен
вдоль потока, `Cl` — перпендикулярно ему в плоскости XY:
`Cd = Cx*cos(alpha) + Cy*sin(alpha)`,
`Cl = -Cx*sin(alpha) + Cy*cos(alpha)`. При `alpha=0` они совпадают с `Cx/Cy`.
Без опорной площади записываются только силы, коэффициенты не вычисляются.

Пример параметров для `configs/hypersonic_wedge.json`:

```text
--wall-temperature 1 --wall-heat-capacity 10 --force-reference-area 0.18
```

Здесь `0.18 = length * width` — выбранная площадь клина в плане, а `10` —
демонстрационная теплоёмкость, не параметр конкретного материала. Для STL
выбирайте площадь явно и сохраняйте её одинаковой при сравнении расчётов.
Все выходные файлы пишутся в рабочий каталог запуска; используйте отдельный
каталог для каждого расчёта.

### Визуализация поверхности и интегральных характеристик

Общая команда `tools/plot_fields.py RUN --gif` автоматически добавляет
визуализации тела, если в каталоге есть новые CSV. Для построения только
по поверхностным данным и силам (без газовых снимков):

```bash
python3 tools/plot_body.py output/my-run --gif
```

В `RUN/plots` (или каталоге `--out`) создаются:

- `surface_temperature.png` — трёхмерная сетка тела, цвет каждого
  треугольника соответствует его температуре в последнем снимке;
- `surface_history.png` — средняя температура с весами по теплоёмкости,
  диапазон min–max полигонов и суммарное поглощённое тепло;
- `surface_temperature.gif` при `--gif` — нагрев поверхности с общей
  цветовой шкалой для всех времён и фиксированным ракурсом;
- `body_forces.png` — силы Fx/Fy/Fz за шаг и их средние с начала расчёта;
- `body_coefficients.png` — Cx/Cy/Cz и Cd/Cl за шаг и их средние, если
  при расчёте была задана опорная площадь.

Время берётся из CSV, снимки сортируются по времени; дублирующий финальный
снимок не добавляет второй кадр. Длительность кадров GIF пропорциональна
интервалам модельного времени (с минимальным кадром 20 мс), последний
кадр задерживается. Газовая и поверхностная температуры имеют отдельные
цветовые шкалы. Для изотермического расчёта без поверхностных снимков
строятся только доступные графики сил и коэффициентов. Старые расчёты
без новых CSV обрабатываются `plot_fields.py` как прежде.

### Клин и температура стенки

Отражение от тела диффузное, с полной тепловой аккомодацией. Температура
стенки задаётся `wall_temperature` в JSON или `--wall-temperature` в CLI
и по умолчанию равна 1 в единицах температуры газа. Допустимы только
конечные положительные значения. В отличие от зеркального отражения,
такое тело обменивается с газом импульсом и энергией. При холодной стенке
плотный охлаждённый слой не следует автоматически считать налипшей волной.

`configs/hypersonic_wedge.json` задаёт конечный клин и сетку 160×80×20.
Для сравнения используйте также `--ncx 80 --ncy 40`, сохранив `np`.
У текущего генератора клина высота равна `length*sin(alpha)`, поэтому
геометрический угол поверхности — `atan(sin(alpha))`: при параметре 15°
он равен 14,5108°. Эта историческая геометрия здесь не изменяется.

Для острого клина начало присоединённой косой волны на вершине физически
нормально; дальше её наклон должен отличаться от наклона поверхности.
[NASA описывает невязкий двумерный ориентир](https://www.grc.nasa.gov/WWW/BGH/oblique.html).
Он не является точным эталоном для конечного трёхмерного клина с диффузной
стенкой и разреженным газом. Для одноатомного газа используем `gamma=5/3`.

После сохранения фактических `config.json`, `run.log`, `initial.dat`,
`final.dat` и `data*.dat` для двух клиньев и двух кубов на одинаковой сетке
с разными температурами стенки:

```bash
python3 tools/wedge_wall_report.py --coarse results/wedge-coarse \
    --fine results/wedge-fine --cold results/cube-cold \
    --warm results/cube-warm --out results/wedge-report
```

Скрипт строит поля, поперечные профили клина, сравнение стенок куба и две
анимации. Среднее берётся за последнюю треть расчёта; GIF — до трёх
последовательных снимков. Плотность `N/np` относится к полной ячейке:
для ячеек, пересечённых телом, это заниженная оценка плотности газа.
Поэтому при определении расстояния до контура `N/np=1.5` исключаются
пересечённые и ближайшие к стенке ячейки. Этот контур — условный индикатор,
не точное положение ударной волны. Проверки влияния Z, размера области,
шага и статистики требуются отдельно.

Нормировка столкновений использует постоянное опорное число модельных частиц
`N0` на полную ячейку и текущую плотность:
`Kn_local = Kn * N0 * (Vgas/Vcell) / N`. При изменении статистического веса
числа `N` и `N0` меняются вместе; при физическом сжатии газа меняется только
`N`. В CLI опорная плотность равна `np*ncx*ncy*ncz/(lx*ly*lz)`.
Для самостоятельно заполненных пустых `Cell` опорное число задаётся через
`SetReferenceParticleCount`; оно не пересчитывается при притоке и оттоке.

Каждая попытка выбирает две различные частицы случайно из всей ячейки.
Число пар учитывается как `N*(N-1)/2`; верхняя граница относительной скорости
вычисляется по максимальной скорости относительно среднего потока и
поддерживается после столкновений. Проверки релаксации встречных пучков
сравнивают 32, 128 и 512 частиц, порядок массива и разбиение времени,
одновременно проверяя сохранение импульса и энергии.

Старые прогоны до этого исправления использовали опорное число 1 и фактически
`Kn/N`; их нужно пересчитать перед количественными сравнениями. Исправление
нормировки не является полной валидацией решателя: оценка газового объёма
пересечённых телом ячеек и сходимость пространственной сетки требуют отдельной
проверки. При пяти и менее частицах существующая модель пропускает столкновения;
для исследования независимости от статистики следует избегать такого режима.

### Гиперзвуковой поток и `hyperfree`

`hyperfree` задаёт внешний максвелловский резервуар: выходящие частицы
покидают область, входящие имеют распределение нормальной скорости
`p(w) ∝ w exp(-(w-u)²/(2T)), w > 0`. Тангенциальные скорости нормальны
с дисперсией `T`. Частицы входят через грань в случайный момент шага,
проходят оставшееся время и проверяются на столкновение с телом.
Поток учитывает входящий тепловой хвост даже на выходной границе.
Описание такого подхода к резервуару есть также в
[OpenFOAM DSMC FreeStream](https://github.com/OpenFOAM/OpenFOAM-dev/blob/master/src/lagrangian/DSMC/submodels/InflowBoundaryModel/FreeStream/FreeStream.C).

Для внешнего обтекания все шесть **дальних** граней можно сделать `hyperfree`.
Это не требование для любой гиперзвуковой задачи: стенки, плоскости симметрии
и периодические границы имеют другие условия. Границы резервуара должны быть
достаточно далеко от возмущённого потока; влияние размера области проверяется отдельно.

`configs/hypersonic_cube.json` задаёт куб размером 0,2, `S=5`
(равновесный `M≈5,48`), `Kn=0,02`, все шесть граней `hyperfree`,
сетку 160×40×20 и примерно 2 млн частиц. Для сравнения используйте
80×40×20, затем контроль без тела:

```bash
make run CONFIG=configs/hypersonic_cube.json OUTPUT_DIR=results/fine
make run CONFIG=configs/hypersonic_cube.json OUTPUT_DIR=results/coarse ARGS="--ncx 80"
make run CONFIG=configs/hypersonic_cube.json OUTPUT_DIR=results/control ARGS="--ncx 80 --geometry-type none"
```

Для `tools/shock_profile.py` в каждом каталоге нужны `run.log` с выводом
решателя и `config.json` с фактическими параметрами (включая переопределения CLI),
а также `initial.dat`, `final.dat` и промежуточные `data*.dat`:

```bash
python3 tools/shock_profile.py --coarse results/coarse --fine results/fine \
    --control results/control --out results/report
```

Скрипт сравнивает профили в центральной трубке перед телом за последнюю
треть расчёта. Переход `uₓ/√(5T/3)=1` служит индикатором положения фронта,
а не точным определением ударной поверхности в неравновесном газе.
Максимальный градиент плотности выводится отдельно: он может находиться
в пристеночном слое. Удвоение числа ячеек только по X проверяет разрешение
вдоль потока, но не заменяет сходимость по всем осям, шагу и размеру области.
Глобальная дисперсия скорости в контрольном расчёте позволяет проверить
температуру без смещения локальной оценки при малом числе частиц в ячейке;
при наличии тела она включает пространственную неоднородность средней скорости.

Solver записывает результаты в текстовые файлы с разделителем `;`:
`data.dat`, `data<t>.dat`, `speed.dat`, `time.dat`. Для их оперативного просмотра
добавлены вспомогательные скрипты на Python 3 (`numpy`, `pandas`, `matplotlib`):

- `tools/plot_snapshot.py` — строит срез по выбранной плоскости (`xy`, `xz`, `yz`)
  и отображает выбранное поле (`ro`, `T`, `vx`, `vy`, `vz`, `E`), при желании
  накладывая векторную карту скоростей. Для управления разрешением можно задать
  `--dpi` (плотность пикселей) и/или `--figsize WIDTH HEIGHT` (размер холста в
  дюймах):
  ```bash
  python3 tools/plot_snapshot.py --input build/data.dat --plane xy \
      --z-value 0.0 --thickness 0.05 --field T --show-cbar \
      --dpi 300 --figsize 10 8 \
      --show-velocity --quiver-step 3 --quiver-color white
  ```
  Аргументы `--show-velocity`, `--quiver-step`, `--quiver-scale` и
  `--quiver-color` управляют наложением стрелок скорости на выбранной плоскости.
- `tools/generate_gif.py` — собирает последовательность файлов `data*.dat`
  в анимированный GIF. Поддерживает те же настройки среза и отображения, что и
  `plot_snapshot.py`, включая `--dpi` и `--figsize` для контроля разрешения кадров.
  Пример:
  ```bash
  python3 tools/generate_gif.py --pattern "build/data*.dat" --plane xy \
      --z-value 0.0 --thickness 0.05 --field T --show-velocity \
      --quiver-step 3 --fps 8 --dpi 200 --figsize 12 9 --out plots/run.gif
  ```
  Дополнительно можно задать `--frame-step`, `--max-frames`, `--vmin/--vmax` для
  контроля длительности и цветовой шкалы.
- `tools/monitor_simulation.py` — следит за последним файлом `data<t>.dat` и
  обновляет график каждые несколько секунд (удобно запускать параллельно расчёту):
  ```bash
  python3 tools/monitor_simulation.py --directory build --plane xy --coord 0.0
  ```

Необходимые пакеты:
```bash
python3 -m pip install numpy pandas matplotlib pillow
```

### Управление случайными числами

`--seed 123` (или `"seed": 123` в конфигурации) задаёт базовый seed uint32.
Без него seed выбирается случайно; фактическое значение выводится при запуске.
Генератор — PCG32 XSH-RR (`pcg32-xsh-rr-v1`); его идентификатор также
выводится при запуске. Базовый seed передаётся как initial state, индекс ячейки —
как stream selector при стандартной инициализации PCG. Допустимы идентификаторы
потока от 0 до 2⁶³−1; большие значения отклоняются до изменения состояния.

Переход с `mt19937` меняет последовательности при прежнем seed. Повторные
однопоточные запуски воспроизводимы в рамках одной сборки; распределения и
`std::shuffle` остаются стандартными и могут различаться между реализациями
стандартной библиотеки. Исходный алгоритм адаптирован из
[pcg-c-basic, revision bc39cd76](https://github.com/imneme/pcg-c-basic/tree/bc39cd76ac3d541e618606bcc6e1e5ba5e5e6aa3),
лицензия — [Apache-2.0](third_party/pcg/LICENSE.txt).

Каждая ячейка использует собственный поток случайных чисел, связанный с её
индексом, независимо от рабочего потока. Порядок параллельного переноса частиц
остаётся недетерминированным: одинаковый seed не гарантирует побитового
совпадения траекторий при многопоточном расчёте.

### Замеры производительности

Для повторяемых коротких прогонов без промежуточных снимков:

```bash
python3 tools/benchmark_solver.py --binary build/MC3dSolver --out /tmp/mc3d-benchmark --repeats 5
```

Скрипт запускает сетку 24×12×8 с 60 частицами на ячейку, `seed=123`,
`end_time=0.05`, без тела, с кубом и клином при 1 и 4 потоках. Он сохраняет
конфигурации, логи и `summary.json`. Время всего процесса включает инициализацию;
`ClusterStep` измеряет шаг расчёта, а `CheckBodyParticles` — диагностику
проникновения в тело. Таймеры используют монотонные часы без округления до
миллисекунд. Для сравнения используйте одинаковую машину и Release-сборки;
чередуйте старый и новый бинарники, чтобы уменьшить влияние нагрузки машины.

Контрольный замер на macOS/AppleClang: медианы пяти прогонов каждого варианта,
с чередованием бинарников до и после кеширования геометрии и укрупнения задач.

| Геометрия | Потоки | Шаг до, мс | Шаг после, мс |
|---|---:|---:|---:|
| Без тела | 1 | 16.22 | 14.85 |
| Без тела | 4 | 8.93 | 7.92 |
| Куб | 1 | 35.99 | 14.59 |
| Куб | 4 | 24.65 | 7.25 |
| Клин | 1 | 43.73 | 29.87 |
| Клин | 4 | 25.79 | 15.30 |

Это результаты небольших сценариев, а не гарантия ускорения на других сетках.
Однопоточные итоговые снимки совпали побайтово. В многопоточных прогонах порядок
переноса частиц может менять траектории и количество шагов, поэтому сравнивается
среднее время шага каждого прогона, затем медиана этих средних.

Геометрия подготавливает кеш bounds, допуска и данных треугольников до запуска
расчёта. Для каждого треугольника сохраняются первая вершина, два ребра и множитель
порога параллельности: 80 байт на полигон при 24-байтовом `Point`, без учёта
служебных данных контейнера. Подготовленные запросы только читают кеш; без
подготовки данные вычисляются из исходных полигонов. `IsInnerPoint()` прекращает
голосование после двух отрицательных ответов; положительное большинство требует
проверки оставшегося луча на близость к поверхности. Её штатные
методы изменения сбрасывают кеш; подклассы, меняющие вершины или набор полигонов
напрямую, должны вызывать `InvalidateQueries()`. Подготовка и изменение геометрии
не должны выполняться одновременно с запросами рабочих потоков.

### Память генератора случайных чисел

Состояние `RandomStream` занимает 16 байт вместо 2504 в контрольной сборке
macOS/AppleClang с libc++ (−99,36%; размер прежнего `mt19937` зависит от библиотеки).
Владение потоками через `shared_ptr` и привязка к ячейкам сохранены.

```bash
python3 tools/benchmark_rng_memory.py --before /path/to/old/MC3dSolver \
    --after build/MC3dSolver --out /tmp/mc3d-rng-memory
python3 tools/benchmark_solver.py --baseline /path/to/old/MC3dSolver \
    --binary build/MC3dSolver --out /tmp/mc3d-rng-speed --repeats 5
```

Замер памяти: пустые сетки, `np=0`, `end_time=0`, без вывода снимков, один поток.
Каждый образец запускается отдельным процессом; RSS включает всю память солвера.
Время включает запуск процесса и инициализацию. Ниже одиночные замеры на macOS,
Release, до и после замены RNG; это не медианы повторных запусков.

| Сетка | RSS до, МиБ | RSS после, МиБ | Время до, с | Время после, с |
|---|---:|---:|---:|---:|
| 32³ | 106.2 | 22.0 | 0.554 | 0.328 |
| 64³ | 834.2 | 160.5 | 1.156 | 0.133 |
| 80³ | 1626.9 | 311.8 | 2.252 | 0.243 |

На 80³ пиковый RSS всего процесса снизился на 80,8%.

Сравнение шага расчёта после замены RNG: медианы пяти чередующихся прогонов
на тех же небольших сценариях. Последовательности RNG и траектории изменились,
поэтому сравнивается время на шаг. Регрессий в этих замерах не обнаружено.

| Геометрия | Потоки | Шаг mt19937, мс | Шаг PCG32, мс |
|---|---:|---:|---:|
| none | 1 | 12.23 | 10.51 |
| none | 4 | 5.96 | 5.41 |
| cube | 1 | 12.26 | 11.29 |
| cube | 4 | 5.97 | 5.48 |
| wedge | 1 | 27.35 | 26.42 |
| wedge | 4 | 13.37 | 12.66 |

Два повторных однопоточных запуска PCG32 с `seed=123` дали побайтово
одинаковые итоговые снимки для каждой из трёх геометрий. Совпадение со снимками
прежнего генератора не предполагается.

### Пакетное распределение частиц

`DistributeParticles()` объединяет последовательные принятые частицы с одной
целевой ячейкой в пачку и добавляет её под одной блокировкой. Сортировки нет;
однопоточный порядок совпадает с прежним
приёмом по одной частице. При нескольких потоках порядок пачек одной ячейки
зависит от выполнения задач. Остаток вне ячеек сохраняет исходный порядок.
Сбор частиц, передача соседям и порядок граничных условий не изменены.

Каждая задача переиспользует один массив индексов текущей пачки и буфер остатков.
Дополнительная память индексов — O(N) в худшем случае; таблиц размером
«число ячеек × число потоков» нет. Ёмкость целевых векторов растёт геометрически,
чтобы небольшой приток не вызывал выделение памяти каждый шаг.

Для увеличенного сценария сравнения:

```bash
python3 tools/benchmark_solver.py --baseline /path/to/old/MC3dSolver \
    --binary build/MC3dSolver --out /tmp/mc3d-transfer-large --repeats 5 \
    --grid 48 24 16 --particles 120 --threads 1 4 8 --geometries none
```

Значения по умолчанию benchmark остаются прежними: сетка 24×12×8, 60 частиц,
1/4 потока и геометрии `none`, `cube`, `wedge`.

На изолированном Ubuntu/GCC Release runner, по пяти чередующимся прогонам,
суммарное время двух фаз распределения снизилось на 11–37% в стандартных
сценариях и на 15–27% в увеличенном сценарии. Полный шаг ускорился на 1–8%
во всех девяти случаях. Это результаты конкретных сценариев; многопоточный
порядок поступления частиц и траектории могут различаться.
